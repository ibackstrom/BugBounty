A Path Prefix That Walked Past Cloudflare on an Open Banking API

----[ Target

The target is an open banking platform that aggregates account data, transactions, and payroll records from banks across Latin America. Production traffic terminates on api.belvo.com. The sandbox environment, used by integrators in development, lives on sandbox.belvo.com. Both sit behind Cloudflare with a managed challenge enabled at the zone level.

----[ Observation

A request for the document root triggers the standard challenge:

$ curl -sI https://sandbox.belvo.com/
HTTP/2 403
server: cloudflare
cf-mitigated: challenge

A request for the API root, on the same hostname, does not:

$ curl -s https://sandbox.belvo.com/api/ -H "Accept: application/json"
[{"message":"Authentication credentials were not provided.",
  "code":"not_authenticated",
  "request_id":"1f8f3536ec7944c39a386da82d5c0eea"}]

The response is a JSON error from the origin Django application. Cloudflare is no longer in the path. The same behavior holds for every documented API route:

GET  /api/institutions/
GET  /api/accounts/
GET  /api/transactions/
GET  /api/links/

A second prefix shows the same property. The ACME HTTP-01 validation path is excluded from the challenge as well, and returns origin responses for arbitrary names:

$ curl -s -o /dev/null -w "%{http_code}\n" \
    https://sandbox.belvo.com/.well-known/acme-challenge/test
404

----[ Method Surface

The bypass applies per HTTP method. The following methods reach the origin:

GET, POST, OPTIONS

The following are intercepted by Cloudflare and answered with a challenge or a 405:

PATCH, DELETE, TRACE

The asymmetry is consistent across both the sandbox and production hosts. It indicates that the rule set targets browser-shaped traffic on root paths, while the JSON API and a small set of operational paths were carved out for client compatibility.

----[ Why It Matters

The endpoints behind the bypass require authentication. None of the calls above leak data on their own. The bypass is not a direct read primitive. What it does is remove the cost of every other test that follows.

o  Wordlists run at line speed against the origin without
   solving challenges or rotating residential proxies.

o  Authentication probes (Bearer, Basic, session cookies) can
   be differentiated by error code without WAF interference.

o  Any future bug in the API stack is reachable from any
   network, with no challenge layer in front of it.

o  Rate limiting that depends on the WAF identifying the
   client is not in force on the API path.

For a regulated financial data aggregator, the API surface is the asset. Removing the layer that was bought to defend it changes the posture of the entire perimeter.

----[ Remediation

The Cloudflare zone configuration must apply the same managed challenge to the API path and to the .well-known path that it applies to the document root. Where the challenge interferes with client SDKs, a bot management rule with API-aware verification is the documented replacement. Either approach restores symmetry between the routes and removes the prefix as a discriminator.

----[ Closing

The flaw is not in Cloudflare and not in the application. It is in the rule that connects the two. A single path prefix decides whether a request is treated as a browser session or as a trusted machine call, and the prefix is published in the public API documentation.

Reported.

A perimeter is only as wide as the narrowest rule that defines it.
